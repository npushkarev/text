Куда класть upstream-источники (<pkg>/src/*.tar.gz) — коротко
  
  Что это вообще

  Tarball'ы с github (v1.60.1.tar.gz, etc.) — нужны для offline-сборки на closed-network. Conan по умолчанию делает wget из conandata.yml URL → на закрытой сети
  падает. Наш _offline_source_archive() берёт их локально.

  4 варианта где разместить

  1. В git-репо рядом с recipes (текущий вариант)

  conan-recipes/
  ├── grpc/src/v1.60.1.tar.gz        66 MB
  ├── grpc/src/v1.78.1.tar.gz        58 MB
  ├── protobuf/src/v4.25.2.tar.gz    ...
  └── ...

  ┌──────────────────────────────────────┬───────────────────────────────────────────┐
  │                Плюсы                 │                  Минусы                   │
  ├──────────────────────────────────────┼───────────────────────────────────────────┤
  │ Простота — клонируешь репо, всё есть │ git clone тяжёлый (~600 MB+)              │
  ├──────────────────────────────────────┼───────────────────────────────────────────┤
  │ Воспроизводимость bit-by-bit         │ git pull тащит большие файлы при ребейзах │
  ├──────────────────────────────────────┼───────────────────────────────────────────┤
  │ Нет внешних зависимостей при сборке  │ Растёт .git history                       │
  └──────────────────────────────────────┴───────────────────────────────────────────┘

  Когда использовать: мало пакетов (до 10), редкие апгрейды.

  2. Git LFS (Large File Storage)
  
  git lfs track "*/src/*.tar.gz"
  git add .gitattributes

  ┌─────────────────────────────┬─────────────────────────────────────────┐
  │            Плюсы            │                 Минусы                  │
  ├─────────────────────────────┼─────────────────────────────────────────┤
  │ git clone стал лёгкий       │ Нужен LFS-сервер (Bitbucket/GitHub LFS) │
  ├─────────────────────────────┼─────────────────────────────────────────┤
  │ Tarball'ы тянутся on-demand │ Закрытая сеть — нужен self-hosted LFS   │
  ├─────────────────────────────┼─────────────────────────────────────────┤
  │ .git history не растёт      │ Лишний слой инфры                       │
  └─────────────────────────────┴─────────────────────────────────────────┘
  
  Когда использовать: репо вырос > 1 GB, есть свой LFS endpoint.

  3. ProGet asset feed
  
  proget.inc.elara.local/feeds/sources/
  └── grpc/v1.60.1.tar.gz

  Патч в _offline_source_archive():
  url_env = os.environ.get("ELARA_SOURCES_PROGET",
                           "https://proget.inc.elara.local/feeds/sources/")
  # wget оттуда если нет локально

  ┌──────────────────────────────────────────────┬──────────────────────────────────────────────────┐
  │                    Плюсы                     │                      Минусы                      │
  ├──────────────────────────────────────────────┼──────────────────────────────────────────────────┤
  │ Sources централизованы, один источник истины │ Требует доп.фичи в ProGet (asset feed)           │
  ├──────────────────────────────────────────────┼──────────────────────────────────────────────────┤
  │ Git-репо тощий                               │ DevOps support нужен — загрузка tarball'ов       │
  ├──────────────────────────────────────────────┼──────────────────────────────────────────────────┤
  │ Можно версионировать                         │ Каждый билд должен иметь сетевой доступ к ProGet │
  └──────────────────────────────────────────────┴──────────────────────────────────────────────────┘

  Когда использовать: уже используется ProGet, хотите единый pipeline.

  4. NFS / shared mount
  
  # на dev-VM / TC-агенте:
  mount -t nfs storage:/srv/upstream-sources /mnt/sources
  rm -rf grpc/src
  ln -s /mnt/sources/grpc grpc/src

  ┌────────────────────────────────────┬───────────────────────────────────────────┐
  │               Плюсы                │                  Минусы                   │
  ├────────────────────────────────────┼───────────────────────────────────────────┤
  │ Один общий store на много агентов  │ Точка отказа — NFS down → билды стоят     │
  ├────────────────────────────────────┼───────────────────────────────────────────┤
  │ Не нужно копировать в каждый клон  │ Нужно настраивать mount на каждом агенте  │
  ├────────────────────────────────────┼───────────────────────────────────────────┤
  │ Простая логика загрузки tarball'ов │ Permissions / locking могут конфликтовать │
  └────────────────────────────────────┴───────────────────────────────────────────┘

  Когда использовать: есть готовый NFS-сервер, много агентов одинаковой архитектуры.

  Текущий размер — приемлемый. Git pull/clone терпимый. Менять не надо.

  Если репо вырастет — миграция в LFS

  # Одна команда:
  git lfs migrate import --include="*/src/*.tar.gz" --everything

  # Push:
  git push --force origin master      # ВНИМАНИЕ: переписывает history

  После этого git clone тянет только метаданные tarball'ов, сам файл — при первом git checkout.

  Контракт filename (важно!)

  Filename должен match'ить URL filename из conandata.yml:

  # conandata.yml:
  sources:
    "1.60.1":
      url: "https://github.com/grpc/grpc/archive/refs/tags/v1.60.1.tar.gz"
                                                            ^^^^^^^^^^^^
                                                            filename

  → grpc/src/v1.60.1.tar.gz

  Иначе _offline_source_archive() не найдёт → fallback на любой .tar.gz в src/ (опасно если их несколько) → может схватить не ту версию.

  TL;DR
  
  1. Сейчас в git — норма. Не трогать пока репо <1 GB.
  2. Filename = filename из URL. Иначе сборка возьмёт левый tarball.
  3. Когда вырастет → Git LFS (1 команда миграции).
  4. На production-CI с многих агентов → ProGet asset feed в долгосрочной перспективе.
