  Варианты для Linux+Docker агентов

  Вариант A — Docker named volume per-agent (рекомендую как минимум)
  
  В TC build step:
  docker run --rm \
      -v conan-cache-${ARCH}-${BUILD_TYPE}:/root/.conan2 \
      -v ${WORK_DIR}:/work \
      grpc-tc-mirror \
      /work/conan-recipes/test-astra/run_grpc_1601_upstream.sh
      
  ┌─────────────────────────────────────────────────────────────────────┬─────────────────────────────────────────────────────────────────┐
  │                                Плюсы                                │                             Минусы                              │
  ├─────────────────────────────────────────────────────────────────────┼─────────────────────────────────────────────────────────────────┤
  │ Cache переживает container-restart                                  │ На каждом агенте свой cache — первая сборка с нуля              │
  ├─────────────────────────────────────────────────────────────────────┼─────────────────────────────────────────────────────────────────┤
  │ Простая настройка — Docker сам управляет (/var/lib/docker/volumes/) │ Если несколько билдов на одном агенте параллельно — SQLite-lock │
  ├─────────────────────────────────────────────────────────────────────┼─────────────────────────────────────────────────────────────────┤
  │ Очистка через docker volume rm                                      │ Контейнер не видит cache другого агента                         │
  └─────────────────────────────────────────────────────────────────────┴─────────────────────────────────────────────────────────────────┘

  Это то что у нас сейчас в run_grpc_1601_upstream.sh через CACHE_VOLUME.

  Вариант B — Bind mount на TC agent persistent dir

  docker run --rm \
      -v /opt/teamcity-agent/conan-cache:/root/.conan2 \
      -v ${WORK_DIR}:/work \
      grpc-tc-mirror \
      /work/conan-recipes/test-astra/run_grpc_1601_upstream.sh

  ┌──────────────────────────────────────────────────────────────┬───────────────────────────────────────────────────────────┐
  │                            Плюсы                             │                          Минусы                           │
  ├──────────────────────────────────────────────────────────────┼───────────────────────────────────────────────────────────┤
  │ Видно с host'а — легко бэкапить, обрезать, мониторить размер │ Permissions требуют внимания (chown 0:0 на /root/.conan2) │
  ├──────────────────────────────────────────────────────────────┼───────────────────────────────────────────────────────────┤
  │ Можно настроить TC чтобы не чистить эту директорию           │ UID mismatch между container и host                       │
  └──────────────────────────────────────────────────────────────┴───────────────────────────────────────────────────────────┘

  Вариант C — tmpfs для билда (агрессивная оптимизация)

  docker run --rm \
      --tmpfs /root/.conan2:size=12G \
      -v ${WORK_DIR}:/work \
      grpc-tc-mirror \
      bash -c 'cd /work/conan-recipes && ./test-astra/run_grpc_1601_upstream.sh'

  Cache в RAM → линковка static grpc (482 MB) ускоряется на ~25-30%. Но каждая TC сборка стартует с нуля — нет переиспользования.

  ┌──────────────────────┬─────────────────────────────────────────────────────┐
  │        Плюсы         │                       Минусы                        │
  ├──────────────────────┼─────────────────────────────────────────────────────┤
  │ Самая быстрая сборка │ RAM-критично: на 16 GB агенте → OOM при сборке grpc │
  ├──────────────────────┼─────────────────────────────────────────────────────┤
  │ Не растёт диск       │ Каждый билд = всё с нуля → дольше первая итерация   │
  └──────────────────────┴─────────────────────────────────────────────────────┘

  Подходит для CI smoke где быстро + независимо ценнее переиспользования.

  Вариант D — Pre-baked image с уже собранными deps (см. run_prebake.sh)

  У нас уже есть скрипт test-astra/run_prebake.sh — он собирает grpc-tree один раз, коммитит в Docker image, пушит на ProGet. Тогда TC pull'ит готовый image:

  1. Раз в неделю/месяц: run_prebake.sh
     - Берёт чистый grpc-tc-mirror
     - Гонит run_grpc_1601_upstream.sh внутри
     - Cleanup + docker commit → grpc-tc-mirror-prebaked
     - docker push proget.inc.elara.local/main/library/grpc-tc-mirror-prebaked:YYYYMMDD

  2. На каждом TC билде:
     docker pull proget.inc.elara.local/.../grpc-tc-mirror-prebaked:YYYYMMDD
     docker run ... (Conan cache УЖЕ ВНУТРИ image'а)

  ┌─────────────────────────────────────────┬───────────────────────────────────────────┐
  │                  Плюсы                  │                  Минусы                   │
  ├─────────────────────────────────────────┼───────────────────────────────────────────┤
  │ Сборка downstream ~30 сек (всё в cache) │ Pre-bake надо переделать при смене recipe │
  ├─────────────────────────────────────────┼───────────────────────────────────────────┤
  │ TC агенты не нужно warming up           │ Image весит много (8-15 GB)               │
  ├─────────────────────────────────────────┼───────────────────────────────────────────┤
  │ Версионирование cache через image tag   │ Логистика — кто и когда перепекает        │
  └─────────────────────────────────────────┴───────────────────────────────────────────┘

  Это рекомендуемая стратегия для production-CI с частыми билдами downstream'ов которые потребляют конкретный набор grpc/protobuf/abseil-версий.

  Вариант E — ProGet как canonical Conan binary-cache (длительная стратегия)

  Завести Conan remote на ProGet, после каждого билда конан-агенты делают conan upload:

  # Однократно на каждом агенте:
  conan remote add elara-proget https://proget.inc.elara.local/api/v2/repository/conan/

  # После сборки рецепта:
  conan upload "grpc/1.60.1@" --remote=elara-proget --all --confirm

  # На следующем билде где угодно:
  conan install --requires=grpc/1.60.1 -r=elara-proget --build=never

  ┌─────────────────────────────────────────────────────────────────────┬─────────────────────────────────────────────────┐
  │                                Плюсы                                │                     Минусы                      │
  ├─────────────────────────────────────────────────────────────────────┼─────────────────────────────────────────────────┤
  │ Все агенты делятся cache через ProGet — собрали раз, используют все │ ProGet нужен Conan-feed (отдельная фича)        │
  ├─────────────────────────────────────────────────────────────────────┼─────────────────────────────────────────────────┤
  │ Можно мигрировать на новые агенты без потерь                        │ Требует настройки conan upload в TC build steps │
  ├─────────────────────────────────────────────────────────────────────┼─────────────────────────────────────────────────┤
  │ Хороший backup (артефакты в ProGet bin-cache)                       │ ABI-strict — package_id mismatch → пересборка   │
  └─────────────────────────────────────────────────────────────────────┴─────────────────────────────────────────────────┘

  Долгосрочно — самое правильное. ProGet платный, но фича Conan-feed у инедо есть. Уточни у DevOps есть ли уже Conan-feed или только NuGet.

  Варианты для Windows TC агента
  
  Здесь Docker'а обычно нет — нативный MSVC. Cache живёт прямо на агенте.

  Вариант W1 — Default %USERPROFILE%\.conan2

  :: ничего не настраивать — Conan кладёт в C:\Users\<agent-user>\.conan2\
  conan create grpc/ --version=1.60.1 -pr=win-v143-x64 ...
  Самое простое. Минус: C:\Users\... обычно на system-disk (C:), может закончиться место.
  
  Вариант W2 — Перенаправить через CONAN_HOME

  В TC build configuration → Build Parameters:
  env.CONAN_HOME=D:\conan-cache
  
  Или в build step:
  set CONAN_HOME=D:\conan-cache
  conan create grpc/ ...
  
  Big-disk on D:\ — стандартный паттерн для Windows TC.

  Вариант W3 — Persistent cache в TC agent's system\caches\

  TeamCity сам предоставляет agent-level cache directories что не чистятся между билдами:
  - %system.teamcity.build.tempDir% — per-build, чистится
  - %system.teamcity.agent.work.dir%/../system/caches/ — persistent

  :: В TC build step:
  set CONAN_HOME=%system.teamcity.agent.work.dir%\..\system\caches\conan
  conan create grpc/ ...

  ├──────────────────────────────────────────────────────┼────────────────────────────────────────┤
  │ TC сам знает что это cache — не чистит между билдами │ Привязка к TC-specific переменным      │
  ├──────────────────────────────────────────────────────┼────────────────────────────────────────┤

  Multi-agent concurrency — критическая точка

  Conan SQLite-cache в ~/.conan2/c/ не multi-process safe. Два параллельных билда на одном агенте → SQLite lock → один падает.

  Решения
  
  Изоляция через Docker volumes per-build

  docker run -v conan-cache-${TEAMCITY_BUILD_ID}:/root/.conan2 ...
  # каждый билд — свой свежий volume, никакого переиспользования но безопасно
  Минус: cache не переиспользуется → каждая сборка с нуля.
  
  Изоляция через CONAN_HOME per-build (для Windows)

  set CONAN_HOME=D:\conan-cache\%teamcity.build.id%
  То же — изоляция ценой пересборок.
  
  Сериализация на TC уровне

  В TC build config → Build Triggers / Compatibility / Build Chains: настроить чтобы один тип билда не запускался параллельно на одном агенте
  (maximumNumberOfQueuedBuilds=1 per agent).

  ┌────────────────────────┬─────────────────────────────────┐
  │         Плюсы          │             Минусы              │
  ├────────────────────────┼─────────────────────────────────┤
  │ Cache переиспользуется │ Билды ждут друг друга в очереди │
  └────────────────────────┴─────────────────────────────────┘

  Лучшее решение: ProGet как central binary cache + per-agent ephemeral local cache

  Каждый агент имеет свой маленький локальный cache. Тяжёлые transitive deps скачиваются с ProGet, не пересобираются. Параллельность сохраняется.

  Source-archives (<pkg>/src/*.tar.gz) на TC
  
  Сейчас они в git-репо. TC checkout'ит их каждый раз — это 600+ MB clone. Может быть медленно.

  Варианты:
  1. Git LFS для всех src/*.tar.gz — clone становится быстрый, тарболлы скачиваются on-demand
  2. Pre-mounted NFS на TC агентах: <репо>/zlib/src → /mnt/sources/zlib через bind-mount при docker run
  3. Tarball'ы в ProGet asset feed — wget-fallback в _offline_source_archive() тянет с ProGet если нет локально
  
  Сводные рекомендации

  ┌───────────────────────────────────┬────────────────────────────────────────────────────┬────────────────────────────────────────┐
  │        Уровень оптимизации        │                 Linux+Docker агент                 │             Windows агент              │
  ├───────────────────────────────────┼────────────────────────────────────────────────────┼────────────────────────────────────────┤
  │ Baseline (что собрать минимально) │ Docker named volume conan-cache-<arch> per-agent   │ CONAN_HOME=D:\conan-cache              │
  ├───────────────────────────────────┼────────────────────────────────────────────────────┼────────────────────────────────────────┤
  │ + Multi-agent безопасность        │ Изоляция per build_id, ИЛИ сериализация в TC       │ То же                                  │
  ├───────────────────────────────────┼────────────────────────────────────────────────────┼────────────────────────────────────────┤
  │ + Скорость первой сборки          │ Pre-baked image (run_prebake.sh → ProGet)          │ Cache на D:\ + сохранять между билдами │
